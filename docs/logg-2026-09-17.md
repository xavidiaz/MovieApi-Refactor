## Vad som gjordes — eftermiddag (#92–#96, denna session)

### Steg 4 (#92) — `Exceptions/NotFoundException.cs`

Första gången användaren skapar en custom exception. Guidade genom skillnaden
mellan att **returnera** ett fel som värde (fanns inget stöd för i C# utan
unionstyper) och att **kasta** det — kärnpoängen i hela övningen. Användaren
landade själv på en elegant lösning med primär konstruktor som skickar
formaterat meddelande direkt till basklassen:

```csharp
public class NotFoundException(string entityName, object key)
    : Exception($"{entityName} med id {key} hittades inte.") { }
```

Committat: `Fas 10 Steg 4: Skapa custom exception. Closes #92`.

### Steg 5 (#93) — `MovieService` refaktorerad

Iterativ granskning i flera varv:

- Missförstod initialt `throw` som ett värde i en ternary (`return movie is
  null ? NotFoundException : ...` — kompilerar inte, typerna matchar inte).
  Förklarade att `throw` är ett uttryck som kan stå i en ternary-gren, inte en
  returtyp.
- Provade `??` på ett `bool`-uttryck (`(a != b) ?? throw ...`) — förklarade att
  `??` bara fungerar på nullable vänstersidor, inte bool-villkor; rätt verktyg
  är `if`.
- Dead code hittat två gånger: en redundant `movie is null ? null : ...`
  efter att metoden redan kastat på samma villkor, och en `CreateAsync` som
  fortfarande hade kvar `return null;` för en separat "actors saknas"-check.
- Inkonsekventa entity-namn i felmeddelanden (`"Movie"` / `"Movies"` /
  stavfelet `"Moview"`) — rättat till konsekvent singular `"Movie"`.
- Returtyper bytta från `Task<MovieDto?>` till `Task<MovieDto>` på alla
  metoder som inte längre kan returnera `null` — eftersom `null` inte längre
  är ett giltigt utfall när felet kastas istället.
- Flaggad men inte löst: `NotFoundException("Actors", createDto.ActorsId)`
  skickar in en hel lista som `key` — `ToString()` på en `List<int>` ger inget
  läsbart meddelande. Lämnat som kosmetisk skuld.

Committat: `Fas 10 Steg 5: Refaktorera MovieService att kasta
NotFoundException. Closes #93`.

### Steg 8 (#96) — `GlobalExceptionHandler` + DI-registrering, första riktiga krocken med nytt ramverkskoncept

Helt ny mark för användaren: `IExceptionHandler`-gränssnittet (från .NET 8).
Förklarade formen (`TryHandleAsync` → `true`/`false`) och skrev ett
implementationsförslag som användaren fyllde i.

**Registreringsbuggen (huvudhändelsen idag):** `builder.Services
.AddExceptionHandler<GlobalExceptionHandler>()` + `app.UseExceptionHandler()`
såg korrekta ut men kraschade appen vid start:

```
InvalidOperationException: Either the 'ExceptionHandlingPath' or the
'ExceptionHandler' property must be set in 'UseExceptionHandler()' ...
```

Rotorsak: `UseExceptionHandler()` (utan argument) kräver *antingen* en
`ExceptionHandlingPath`/delegate *eller* `AddProblemDetails()` registrerad som
garanterad fallback — även om en egen `IExceptionHandler` redan finns. Detta
är inte dokumenterat tydligt i felmeddelandet på ett sätt som pekar direkt på
lösningen; själva insikten (att `AddProblemDetails()` krävs *utöver* den
egna handlern) var den svåraste punkten i hela dagens session. Fixat med:

```csharp
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
```

**Öppen, olöst fråga:** `app.UseExceptionHandler()` ligger just nu inuti
`if (app.Environment.IsDevelopment())`, tillsammans med `MapOpenApi()` — vilket
betyder att global felhantering bara är aktiv i utvecklingsläge. Flaggat,
inte löst — användaren har inte tagit ställning än.

Committat: `Fas 10 Steg 8: Skapa global exception handler. Closes #96`
(exakt formulering ej bekräftad i denna session, men steget är avklarat
enligt användaren).

## Flödesbeskrivning — nuläge efter dagens ändringar

```
Controller → XService.XAsync
                 │
                 ├─ hittas/giltig → mapper.Map<XDto>(entity) → 200/204
                 │
                 └─ hittas inte  → throw new NotFoundException(entity, key)
                                        │
                                        ▼
                          GlobalExceptionHandler.TryHandleAsync
                                        │
                         ┌──────────────┴───────────────┐
                    NotFoundException            annan/okänd exception
                         │                               │
                    404 + ProblemDetails      false → ProblemDetailsService
                    (skrivet av handlern)      (fallback, generiskt 500)
```

Alla fyra CRUD-metoder i alla tre services (`Movie`/`Actor`/`Review`) kastar
nu `NotFoundException` istället för att returnera `null` vid "hittades inte".
`GlobalExceptionHandler` fångar bara `NotFoundException` specifikt — allt
annat faller igenom till `AddProblemDetails()`s generiska 500-fallback.

**Ny, oundersökt upptäckt vid sessionens slut:** manuell testning via
Kulala (`.http`-filen) mot en fristående dator (remote control-session) visade
tre 500-fel som *inte* är `NotFoundException` och alltså inte hanteras av
`GlobalExceptionHandler`: `POST /actors/`, `GET /reviews/1`, `DELETE
/reviews/1`. Ingen stack trace tillgänglig än — bara det generiska
ProblemDetails-svaret syntes i Kulala. Rotorsak okänd, kräver `dotnet watch`
-konsolens output för diagnos. `PUT /reviews/1` gav korrekt 400 (Data
Annotations-validering, förväntat beteende, ingen bugg).

## Svårt idag — flaggat för extra övning

- **Exceptions som kontrollflöde, inte returvärde** — den centrala
  begreppsmässiga tröskeln idag. Flera försök att pressa in `throw` i en
  ternary/`??`-position som om det var ett vanligt uttrycksvärde, innan
  mönstret satte sig.
- **`IExceptionHandler`-registreringen kräver `AddProblemDetails()` som
  fallback, även med en egen handler registrerad** — inte uppenbart av
  felmeddelandet, upptäckt genom felsökning tillsammans.
- **Syntax och DI-registreringsordning** (enligt användaren själv: "känns mäst
  krångligt") — var raderna ska stå relativt `builder.Build()`, skillnaden
  mellan `AddExceptionHandler<T>()` (DI-registrering) och
  `UseExceptionHandler()` (middleware-pipeline).
- Återkommande dead-code-mönster: en ternary/villkor som blir oåtkomlig kod
  efter att motsvarande kontroll redan kastat tidigare i samma metod — hände i
  både `MovieService` och `ActorService`, samma buggklass två gånger.

## Kända, avsiktliga begränsningar

- `app.UseExceptionHandler()` aktiv bara i `Development`-miljö — oavsiktlig
  begränsning, inte beslutad, väntar på användarens ställningstagande.
- Endast `NotFoundException` hanteras av `GlobalExceptionHandler` — inga andra
  custom exception-typer finns än (matchar fasplanen, ingen brådska).
