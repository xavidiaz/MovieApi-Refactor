## Vad som gjordes

### DTO-granskning (innan commit av #76)

- **Namespace-bugg**: `MovieDto.cs` hade `namespace MovieApi-Refactor.Dtos;`
  (bindestreck, ogiltigt i C#) — rättat till `MovieApi_Refactor.Dtos`.
- **`Id` saknades i alla DTOs.** Uppklarat missförstånd: DTOs gömmer inte allt
  internt, bara sådant klienten inte behöver eller inte ska se (cykler, känslig
  data). `Id` är den publika identifieraren och behövs i alla läs-DTOs för att
  klienten ska kunna länka vidare (`GET /movies/{id}`, `PUT`, `DELETE`). Lades till
  i `MovieDto`, `MovieSummaryDto`, `ActorSummaryDto`, `ReviewSummaryDto`.
- **Cirkulär struktur mellan summary-DTOs**: `MovieSummaryDto.Actors` →
  `ActorSummaryDto.Movies` → `MovieSummaryDto` (och samma för `Reviews`/`Movie`).
  Löst genom att ta bort tillbaka-referenserna — en summary-DTO nästlad i en annan
  DTO ska vara ett löv, inte peka tillbaka uppåt. Det gjorde också att `MovieDto`
  och `MovieSummaryDto` blev meningsfullt olika (fulla vs. lätta varianten).
- **`ReviewSummaryDto` var tom**, sedan saknade den `Rating` i ett första utkast —
  båda rättade.

### `CreateMovieDto` — designbeslut

- **Ingen `Reviews`** — recensioner skapas separat via `ReviewsController` med egen
  `MovieId`, inte i samma anrop som filmen.
- **Ingen `Id`** — finns inte vid `POST`, databasen sätter den.
- **`Actors` → `ActorsId` (`ICollection<int>`)**, inte `ICollection<ActorSummaryDto>`.
  Resonemang: klienten väljer skådespelare som redan finns i databasen vid
  filmskapande, den ska inte behöva skicka in namn/födelseår igen — bara ID:n.
  (Namnval värt att se över: `ActorIds` hade varit mer följsamt mot konventionen
  än `ActorsId`.)

### Repo-lagret — felaktig avstickare, återställd

Under arbetet med `IMovieService`/`MovieService` flyttades DTO-typerna av misstag
ner i `IMovieRepository`/`MovieRepository` (`Add(CreateMovieDto)` etc.). Det bröt
både kompileringen (`context.Movies` är `DbSet<Movie>`, känner inte till DTOs) och
lagerarkitekturen (Repository ska bara prata `Entity`, DTOs hör hemma vid
Service/Controller-gränsen). Återställt till `Movie` i båda repo-filerna.

### `MovieService` — mappning Movie ↔ MovieDto

- **`GetAllAsync`** — klar. Hämtar `IEnumerable<Movie>` från `unitOfWork.Movies`,
  bygger `MovieDto` per film med `.Select(...)`, nästlade `Select` för
  `Actors`→`ActorSummaryDto` och `Reviews`→`ReviewSummaryDto`.
- **`GetByIdAsync`** — klar efter en runda rättningar (fel användes `=>` istället
  för `=`, tilldelning åt fel håll `movie.Id = dto.Id` istället för
  `Id = movie.Id`, `return movie` istället för `return dto`, saknad null-koll).
  Nu: null-koll direkt efter hämtning, sedan samma mappningsmönster som
  `GetAllAsync` för ett enda objekt.
- **Roslyn IDE0305** ("Collection initialization can be simplified") dök upp —
  `.Select(...).ToList()` byttes mot collection expressions med spread:
  `[.. movie.Actors.Select(...)]`. Tillämpat i både `GetAllAsync` och
  `GetByIdAsync`.
- **`CreateAsync`** — påbörjad, **bygger inte just nu**. Går igenom pseudokod och
  ett första försök som visade en verklig missuppfattning: `Actors = [Id]` i
  entitetsbygget — `Id` fanns inte i scope, och även om den funnits hade en siffra
  inte dugit direkt i `ICollection<Actor>`. Bröt ner till tre steg: (1) tom
  `List<Actor>`, (2) `foreach` över `movieDto.ActorsId` som slår upp varje
  `Actor` via `unitOfWork.Actors.GetByIdAsync(id)` och lägger till om den finns,
  (3) använd den ifyllda listan i `new Movie { ... Actors = actors }`. Sista biten
  (spara + mappa tillbaka till `MovieDto`) återstår att skriva in.
- **`UpdateAsync`/`DeleteAsync`** — orörda, matchar fortfarande inte interfacet
  (`UpdateAsync` tar fortfarande `Movie movie` istället för `CreateMovieDto`, båda
  returnerar entitet istället för `MovieDto`).

## Flödesbeskrivning — målbild när Steg 2 är klar

```
POST /movies
  → MoviesController (skickar CreateMovieDto)
  → serviceManager.Movie
  → MovieService.CreateAsync(CreateMovieDto)
      - slår upp Actor-entiteter via ActorsId
      - bygger ny Movie-entitet
      - unitOfWork.Movies.Add + CompleteAsync
      - mappar sparad Movie → MovieDto (med riktigt Id)
  → SQLite: movies.db
```

`GetAllAsync`/`GetByIdAsync` följer redan detta mönster åt andra hållet
(Entity → DTO). `UpdateAsync`/`DeleteAsync` ska göra samma mappning vid retur.

## Kända, avsiktliga begränsningar

- `MovieRepository.GetAllAsync()`/`GetByIdAsync()` saknar fortfarande
  `.Include(m => m.Actors)`/`.Include(m => m.Reviews)` — även med korrekt
  mappning i servicen kommer `Actors`/`Reviews` visa tomma listor i svaret tills
  det läggs till. Inte åtgärdat än; hör möjligen till ett eget steg nu när DTOs
  löser det tidigare skälet (cirkulär JSON) att undvika `.Include`.
- Inget beslut taget om vad som ska hända om ett ID i `CreateMovieDto.ActorsId`
  inte finns i databasen — just nu tänkt: hoppa över tyst. Riktig validering hör
  till Fas 10.

## Att städa / hålla koll på

- **`CreateMovieDto.Title`/`Year`** använder fortfarande `{ get; set; }` +
  `= string.Empty`-default, inte `{ get; init; }` utan default som resten av
  DTO-laget. Inte rättat än.
- **`ActorsId`** — överväg att byta namn till `ActorIds` för konsekvens med
  vanlig namnkonvention (pluralt substantiv + `Ids`).
- **Arbetsträdet bygger inte just nu** (`CreateAsync` refererar en odefinierad
  `movie`-variabel, `UpdateAsync` matchar inte interfacet). Naturligt läge att
  fortsätta ifrån, men värt att komma ihåg innan nästa `dotnet build`.
