### Review-varvet klart (Fas 6 Steg 19–23)

- **`ReviewService`** – kopierad form från `ActorService`:
  - `GetAllAsync` / `GetByIdAsync` → `unitOfWork.Reviews.*`
  - `CreateAsync` → `Add` + `CompleteAsync`
  - `UpdateAsync(int id, Review review)` → hämta `existing`, kopiera `Rating`
    och `Text`, spara. Rör inte `Movie`-navigation.
  - `DeleteAsync(int id)` → hämta, `Remove`, `CompleteAsync`, returnera.
- **Rättelser i samma commit som Steg 19:**
  - `IReviewService.DeleteAsync` returtyp `Task<Review>` → `Task<Review?>`
    (null för "hittades inte", konsekvent med Movie/Actor).
  - `ReviewService.DeleteAsync` saknade `await unitOfWork.CompleteAsync()` —
    `Remove` markerar bara i change trackern, `DELETE` kördes aldrig mot
    databasen. Bygget var grönt utan varning; ren logikbugg.
  - `IUnitOfWork` saknade `Reviews`-property (bara implementationen `UnitOfWork`
    hade den) → ingen LSP-completion på `unitOfWork.Reviews` i `ReviewService`.
    Lades till i interfacet.

### Fas 7 Steg 1–4

- **`IServiceManager`** – interface i `Services/`, properties `Movie`, `Actor`,
  `Review` (singular, utan `Service`-suffix). Valde detta framför `Movies`/
  `Actors`/`Reviews`; inte helt symmetriskt med `IUnitOfWork` men konsekvent
  inom fasaden.
- **`ServiceManager`** – primär konstruktor `(IUnitOfWork unitOfWork)`.
  Tre `private readonly Lazy<IXService>`-fält, initierade i fältdeklarationen
  med factory-lambda: `new(() => new MovieService(unitOfWork))`. Publika
  properties `=> _xService.Value`. Servicen konstrueras först vid första
  åtkomst — en controller som bara rör `Movie` skapar aldrig `ActorService`
  eller `ReviewService` under den requesten.
  - Övervägt alternativ: `field ??= new MovieService(unitOfWork)` (C# 14
    `field`-nyckelord). Kortare men ej trådsäkert och cachar inte undantag —
    `Lazy<T>` valdes, dels för att issuet kräver det, dels som lärandemoment.
- **DI**: de tre `AddScoped<IXService, XService>()` borttagna, ersatta av
  `AddScoped<IServiceManager, ServiceManager>()`. Efter detta steg: bygget
  grönt men appen trasig i runtime (`Unable to resolve service for type
  'IMovieService'`) tills controllers kopplats om — avsiktligt, därför
  `dotnet build` som verifiering istället för `.http`.
- **Controllers** – alla tre tar nu in `IServiceManager serviceManager` istället
  för varsin service; anropar `serviceManager.Actor.GetAllAsync()` osv.
  Runtime-felet borta. `dotnet build` grönt, alla endpoints svarar.

## Flödesbeskrivning – var är vi nu

```
GET /movies
  → MoviesController (IServiceManager)
  → serviceManager.Movie        (Lazy → MovieService skapas vid första åtkomst)
  → MovieService (IUnitOfWork)
  → unitOfWork.Movies → MovieRepository → context.Movies.ToListAsync()
  → SQLite: movies.db
```

Samma form för `/actors` och `/reviews`. Fasaden (`ServiceManager`) är enda
beroendet i varje controller-konstruktor. `Lazy<T>` gör att bara den efterfrågade
servicen konstrueras per request.

Databasens relationer (oförändrade):

```
Movies ──< Reviews        one-to-many  (FK Reviews.MovieId, cascade)
Movies >──< Actors         many-to-many (join-tabell ActorMovie)
```

## Kända, avsiktliga begränsningar

- Ingen validering att `Review.MovieId` pekar på en existerande film — `POST`
  med påhittat id ger 200. Fas 10 (validering + felhantering).
- `GET`-svar innehåller inte relaterade entiteter (`"reviews": []`,
  `"movie": null`) — repositories gör platt `ToListAsync()`/`FindAsync()` utan
  `.Include`. Medvetet naivt; DTOs i Fas 8 ersätter hela bilden.
- Entities skickas direkt via API:et — DTOs Fas 8, AutoMapper Fas 9.
